# Canvas 렌더링 노트

첫 화면(`/`)의 네 장면은 모두 HTML5 Canvas로 그립니다. 이 문서는 왜 Canvas를 골랐는지, 얼마나 차이가 나는지, 만들면서 부딪힌 문제를 어떻게 풀었는지 정리합니다.

## 왜 Canvas인가

| 장면                | 그리는 것                              | DOM·SVG로 만들면                                                               |
| ------------------- | -------------------------------------- | ------------------------------------------------------------------------------ |
| 첫 화면 로딩 · 제목 | 눈금 60개, 호, 7세그먼트 숫자, 빛 번짐 | 빛 덩어리 16개를 글자 모양으로 오려 내려면 매 프레임 마스크를 다시 계산해야 함 |
| 360도 회전 · 분해   | 960px 이미지 96장 중 1~2장             | `<img>` 96개를 겹쳐 두고 보이기만 바꾸면 디코딩·합성 비용이 늘 남음            |
| 입자 실루엣 · 숫자  | 점 1,800~12,000개                      | 요소마다 스타일 계산·레이아웃·페인트가 따라붙어 수천 개부터 프레임이 떨어짐    |
| 색·재질 구성기 (3D) | 시계 모델 (three.js, WebGL)            | -                                                                              |

Canvas는 요소가 하나뿐이라 무엇을 몇 개 그리든 브라우저가 관리할 노드가 늘지 않습니다. 대신 접근성 트리에는 아무것도 남지 않으므로, 캔버스를 감싼 요소에 `role="img"`와 지금 장면을 설명하는 이름을 붙이고, 같은 내용을 글(설명 목록, 상태 문장)로도 둡니다.

## 성능 비교

`/bench/`에서 같은 궤도 계산으로 점을 움직이며 방식별 평균 FPS와 한 프레임의 스크립트 시간을 잽니다. (점 2×2px, 무대 640×400, 측정 2초)

| 입자 수 | Canvas 2D         | DOM (div + transform) | SVG (rect)         |
| ------: | ----------------- | --------------------- | ------------------ |
|     500 | 60fps (0.1ms)     | 60fps (0.3ms)         | 60fps (0.4ms)      |
|   2,000 | 60fps (0.2ms)     | 60fps (0.8ms)         | 60fps (1.5ms)      |
|   8,000 | 60fps (0.7ms)     | 60fps (3.0ms)         | 60fps (5.3ms)      |
|  20,000 | **60fps (1.7ms)** | **20fps** (7.5ms)     | **26fps** (12.4ms) |

macOS, 헤드리스 Chromium 158에서 잰 값입니다. 같은 환경에서 Lighthouse(모바일)로 첫 화면을 재면 성능 100점, TBT 0ms, LCP 1.4초입니다. CI는 GPU가 없어 소프트웨어 GPU(SwiftShader)가 캔버스 작업을 메인 스레드에서 기다리게 하므로 성능 점수가 60점대로 나오며, 그래서 성능은 경고로만 둡니다. 60fps는 화면 주사율 상한이라, 그 아래에서는 괄호 안의 스크립트 시간이 차이를 보여 줍니다. DOM은 스크립트 시간보다 스타일 계산과 페인트에서 더 많이 잃어 2만 개에서 20fps까지 떨어집니다. 기기마다 다르므로 `/bench/`의 **측정 시작**으로 직접 재 볼 수 있고, 콘솔에서 `await window.__runBench()`를 불러도 됩니다.

## 렌더링 원칙

- **좌표와 루프는 React 밖에 둡니다.** 입자 좌표·속도(`Particle`), 시퀀스 위치(`SequencePlayer`), 빛 꼬리(`HeroRenderer`)는 클래스 안에 있고 컴포넌트는 `useRef`로 붙잡기만 합니다. 매 프레임 바뀌는 값으로 다시 렌더링하지 않습니다.
- **lerp는 프레임 속도와 상관없게** `damp(현재, 목표, λ, dt) = lerp(a, b, 1 - e^(-λ·dt))`를 씁니다. 입자 힘은 60fps 한 프레임을 1로 둔 `step = dt × 60`을 곱합니다.
- **보일 때만 그립니다.** `IntersectionObserver`로 화면 밖 캔버스의 루프를 멈추고, 3D는 `frameloop="never"`로 바꿉니다. 첫 화면은 움직임을 멈춘 뒤 그림이 그대로면 그리기를 건너뜁니다.
- **무거운 것은 늦게 받습니다.** 3D(three.js·R3F·drei)는 구성기 근처에서 `React.lazy`로, lil-gui는 패널을 열 때 받습니다. 시퀀스는 핵심 프레임 25장만 먼저 받고 나머지 71장은 처음 스크롤할 때 받습니다.

## 문제 해결

### 캔버스가 흐릿하다 (DPR)

캔버스의 픽셀 수가 CSS 크기와 같으면 레티나 화면에서 늘어나 흐려집니다. `fitCanvas`(`shared/lib/canvas`)는 `width × devicePixelRatio`만큼 픽셀을 잡고 `ctx.scale(dpr, dpr)`을 걸어 그리기 좌표는 CSS px로 씁니다.

- 크기가 바뀔 때마다 `scale`만 다시 부르면 배율이 곱해져 그림이 커집니다. `setTransform(1, 0, 0, 1, 0, 0)`으로 되돌린 뒤 `scale`합니다.
- `canvas.width`에 같은 값을 다시 넣어도 캔버스가 지워지므로 달라졌을 때만 바꿉니다.
- 창을 다른 배율의 모니터로 옮기면 크기는 그대로인데 배율이 바뀝니다. `ResizeObserver`와 함께 `matchMedia('(resolution: …dppx)')`도 지켜봅니다.
- 배율 3 이상은 픽셀만 늘고 차이가 작아 2에서 자릅니다. (디버그 패널의 **DPR 상한**으로 바꿔 볼 수 있음)

### OffscreenCanvas와 Worker

첫 화면 캔버스는 `transferControlToOffscreen()`으로 Worker에 넘겨, 메인 스레드가 시퀀스·입자·3D로 바빠도 로딩 애니메이션이 끊기지 않게 했습니다. (디버그 패널에서 메인 스레드와 첫 화면 FPS를 따로 볼 수 있음)

- `transferControlToOffscreen()`은 캔버스마다 한 번만 부를 수 있습니다. React StrictMode는 개발 중 effect를 두 번 실행해 `InvalidStateError`가 나므로, 캔버스를 JSX에 두지 않고 effect 안에서 새로 만들어 넣고 정리할 때 뺍니다.
- Worker는 페이지의 `@font-face` 글꼴을 쓸 수 없습니다. 큰 제목은 메인 스레드에서 글꼴이 준비된 뒤 그려 `ImageBitmap`으로 넘깁니다. (전송 목록에 넣어 복사하지 않음)
- `OffscreenCanvas`가 없는 환경(오래된 브라우저, jsdom)에서는 같은 `HeroRenderer`를 메인 스레드에서 돌립니다. 메시지 처리(`applyHeroMessage`)를 함께 써서 두 경로가 갈라지지 않게 했습니다.
- Worker에 `requestAnimationFrame`이 없는 브라우저를 위해 루프(`createFrameLoop`)는 16ms 타이머로 대신할 수 있게 했습니다.

### 루프가 멈추지 않는다 (cancelAnimationFrame)

컴포넌트가 사라진 뒤에도 `requestAnimationFrame`이 남아 있으면 지워진 캔버스에 계속 그리고, 메모리도 놓아주지 않습니다.

- `createFrameLoop`의 `stop()`은 예약해 둔 프레임 번호를 `cancelAnimationFrame`으로 지웁니다. effect 정리 함수에서 꼭 부릅니다.
- 다음 프레임을 먼저 예약한 뒤 `tick`을 부르므로, `tick` 안에서 `stop()`을 불러도 바로 멈춥니다.
- 탭을 오래 숨겼다 돌아오면 `dt`가 커져 입자가 튀므로 0.1초로 자릅니다.

### 시퀀스가 끊기거나 겹쳐 보인다

- 이미지를 `img.decode()`까지 기다린 뒤 씁니다. 그렇지 않으면 첫 `drawImage`에서 디코딩하느라 프레임이 끊깁니다.
- 받지 못한 프레임은 받아 둔 양옆 프레임을 겹쳐 메웁니다(`bracketFrames`). 스크롤이 멈추면 가장 가까운 프레임에 내려앉아 두 장이 겹친 흐릿한 그림으로 머물지 않게 합니다.
- AVIF(알파 포함)를 읽을 수 있는지 1×1 이미지로 한 번 확인하고, 못 읽으면 WebP를 받습니다.

### 그 밖에

- 입자 모양은 화면 밖 캔버스에 글자·이미지를 그려 `getImageData`로 점을 고릅니다. 자주 읽는 캔버스는 `getContext('2d', { willReadFrequently: true })`로 만들어 경고와 GPU 왕복을 피합니다.
- 엔티티의 공개 API가 3D 모델까지 내보내 첫 화면 묶음에 three.js가 딸려 왔습니다. `package.json`의 `sideEffects`에 CSS와 진입점만 남겨, 쓰지 않는 내보내기를 번들러가 덜어 내게 했습니다.
- 3D 조명과 톤 매핑 때문에 베젤의 크림슨 호가 `#8B0000`보다 밝은 분홍으로 보였습니다. 인쇄된 호는 조명을 받지 않는 재질(`toneMapped: false`)로 그리고, 조명별 밝기만 직접 맞춥니다.
